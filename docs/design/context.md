# エージェントの往復と文脈管理の設計（v0.1）

## 往復（エージェントループ）
1. 指示・道具の定義・会話をモデルに送る
2. モデルが道具を呼んだら、モード（`ui.md`）に沿って確認してから実行し、結果を会話に足す
3. モデルが道具を呼ばずに答えたら、1回のやりとりを終える
4. 1回のやりとりの往復が **30回** を超えたら止めて、続けるかを利用者に聞く（安いモデルが同じことをくり返すのを防ぐ）

## 会話の並べ方（キャッシュを効かせる）
`[指示][道具の定義][会話…]` の順にし、先頭は毎回同じにする。会話はうしろに足していくだけにする。先頭が同じなら、その部分はキャッシュ（同じ入力の再利用）で安く読まれる。

過去の会話を書き換える（隠す・要約する）と、そこから先のキャッシュが効かなくなる。そのため書き換えは、しきい値を超えたときにまとめて1回で行う。

## 減らす順番
料金を下げる手段は、キャッシュを壊さないものから使う（DECISIONS.md の 2026-10-26 の項）。
1. 入れる量を減らす: 道具の結果は入れる時点で短くし、全文はファイルに保存する。ファイルは行の範囲か grep で読む。シェル出力の掃除。調べものは subagent。末尾に足すだけなので、どのモデルでもキャッシュを壊さない
2. 出力と推論を減らす: 出力は cache hit の入力の約200倍（DeepSeek）〜50倍（Claude Sonnet 5.5）の単価
3. 過去の会話の書き換え（切り詰め・隠す・要約）: 価格表で元が取れるとき、キャッシュが冷えたとき、質と上限の歯止めが要るときだけ

## トークンを抑える仕組み
| 仕組み | 既定値（推奨値） | 動き |
| --- | --- | --- |
| 道具の結果の上限 | 1件 2,000トークン（ファイルの読み取りは 8,000トークン） | 超えたら全文をファイル（`.ja-harness/out/`）に保存し、大事な行（エラー、一致した行）を先に、残りは先頭と末尾を残して「ほかN行。全文は <パス>」と書く。切り詰めは結果を入れるときの1回だけ。ファイルは行の範囲を指定して続きを読める |
| observation masking（2026-10-28 に改めた） | しきい値より下では、古くなった読み取りと前の依頼の結果だけ | 今の依頼の途中の結果は、しきい値を超えるまで隠さない（本物の DeepSeek で、隠した結果の約8割を読み直し、直近1件だけ残すと合格率が 96% → 41% に落ちた）。古くなった読み取り（読んだあとに同じファイルを書き換えた）と前の依頼の結果は、「残りの往復で浮く料金」が「キャッシュが崩れる損＋読み直しの損」の2倍（`mask.margin`）を超えるときだけ、まとめて1回で隠す。読み直しの見込みは前の依頼の結果 0.4（実測）・古くなった読み取り 0.1。キャッシュが冷えたとき（`cacheTtlSeconds`、既定300秒）は崩れる損を0とみなす。跡は「[Hidden to save tokens: read src/a.ts (1200 tokens). Call the tool again if you need it.]」の1行（restorable）。`mode: "always"` は料金に関係なく隠す（質の確かめ用） |
| しきい値を超えたとき | window（直近5件）の外を全部隠し、足りなければ window の中も古い順に | しきい値の7割（`targetRatio`）まで下げる。下げきれなければ切り詰め → 要約。7割まで下げるのは、すぐまた超えて往復ごとにキャッシュを崩さないため（`bench --sim` で見つけた） |
| 古くなった読み取り | 料金の判断で隠す | 上の observation masking の候補に入れる。読み取りを要約に置き換えることはしない（str_replace が合わなくなるため） |
| 切り詰め（要約の前） | 要約のしきい値を超えたとき | 古い道具の結果のうち長いもの（既定 4,000トークン超）を、先頭と末尾だけを残した形に置き換える。全文は保存したファイルのパスを残す。モデルを呼ばないので安い。これでしきい値を下回れば要約しない。しきい値の下では何もしない |
| LLM-Summary | 文脈が 64Kトークン、またはモデルの上限の50%の小さいほうを超えたら | 切り詰めても足りなければ、古い会話をモデルに要約させて置き換え、直近の生のやりとりは 20Kトークン残す。要約には masking する前の会話を渡し、雛形（下の「要約の作り方」）に沿わせる。要約のあとは最近編集したファイルを読み直す。`/compact` で手動でも実行できる |
| あふれたときの再送 | API が文脈の上限を超えたというエラーを返したとき | しきい値と関係なく、切り詰めと要約で減らせるだけ減らし、同じリクエストを1回だけ送り直す。減らせなければ利用者に知らせて止める |
| 道具の定義は必要なときだけ | MCP の道具 | 組み込みの道具は少数に絞る。MCP の道具は名前と一言だけを見せ、使うときに詳しい定義を読ませる |
| 往復の上限 | 30回で確認 | 超えたら止めて、続けるかを聞く |
| 使った量を見せる | 常に | 状態の行に文脈の割合・トークン・料金、`/context` で内訳 |

## 要約の作り方
- キャッシュに乗せる: 要約のリクエストは、本体の直前のリクエストと同じモデルで、指示・道具の定義・要約する範囲の会話を1字も変えずに並べ、最後に要約の指示を1つ足す。こうすると先頭はキャッシュに当たり、料金がかかるのは要約の指示と要約の出力だけになる。別のモデルに振り分けるとキャッシュが効かないので、要約は本体と同じモデルで行う
- 要約する範囲: 先頭の system prompt は含めない。道具の呼び出しと結果の組は分けない
- 雛形: 決まった見出しで短い箇条書きにする。見出しは、利用者の求め、ファイルと変更、エラーと直し方、残りの作業、今の作業、次の一手、決めたことと制約。空の見出しは「なし」と書き、見出しを消さない。パス・コマンド・エラーの文・数値はそのまま残す。利用者の訂正と指示は正確に残す
- 前の要約がある: 写さずに1つにまとめ直す。まだ正しいことは残し、古くなったことは消す
- 置き換えた要約には、「前の会話をまとめたもの。くり返さずに続きから作業する」と前置きする（英語。`language.modelFacing`）
- 要約が元より短くならなければ、置き換えない

## 料金の計算（masking の判断）
価格表は `prices` に、モデルごとに `input`（キャッシュなし）・`cachedInput`・`cacheWrite`・`output`（100万トークンあたりのドル）で持つ。応答の usage に料金が入っていれば（OpenCode Go の `opencode.list_cost` など）、それで表を確かめる。

隠すかどうかは、次の比べ方で決める（調査レポートの模型。一次資料の式ではないので、測定で確かめる）。
- 損 = 書き換えた位置から末尾までの長さ P を、キャッシュなしで読み直す差額: P × (input − cachedInput)
- 得 = 減るトークン S が、残りの往復 n 回ぶん安く読まれる額: S × cachedInput × n
- n は、そのセッションのここまでの往復の数を目安に見積もる（下限 3）
- 得 > 損 のときだけ隠す

目安: DeepSeek V4.1 Flash では、2,000トークン×10件を隠しても元が取れるまで約97往復かかるので、ほぼ隠さない。Anthropic・OpenAI では約22往復なので、長いセッションでは隠す。

2026-10-28 に、得 > margin ×（損 ＋ 読み直しの損）に改めた。読み直しの損 = 隠す結果ごとに p ×（今の文脈 × cachedInput ＋ その結果 × input）。n は min(10, max(3, ここまでの往復の数))。測定の結果は `bench/RESULTS.md` の 2026-10-28 の項。

LLM-Summary のしきい値（64K か上限の50%）は、料金ではなく質（Context Rot）と上限のための歯止めとして残す。Claude Haiku 5.5 は文脈が 100K トークンを超えると単価が5倍になるので、価格表に段階があるモデルでは、その手前で要約する。

## キャッシュを壊さない決まり
- system prompt に日付や時刻など、毎回変わる値を入れない
- system prompt はセッションの途中で書き換えない。モードの切り替えなどで指示が変わるときは、会話の末尾に短い message として足す
- 道具の一覧と順番はセッションの途中で変えない。MCP の道具を読み込むときは、末尾に足す。モードの違いは道具の定義を変えずに message で伝える
- JSON はキーの順番を固定して書き出す
- 過去のメッセージの書き換え（masking・要約）は、まとめて行う。cache が冷えたとき（idle の後の最初のリクエスト）は、書き換えの好機として使う
- OpenCode Go には `x-opencode-session` をセッションごとに固定して送る
- モデル・effort は、やりとりの区切りでだけ変える。Anthropic では per-message の effort を使う。DeepSeek では、道具を使う会話の過去の `reasoning_content` を常に送り返す（送らないと400になる）
- subagent は、親と同じ system prompt と道具の定義の並びから始める（prefix を共有する）
- 切り替えでキャッシュが効かなくなるときは、状態の行に出す

## キャッシュを測って見せる
- 応答の cached と uncached の入力を毎回記録し、状態の行に hit 率を、`/context` に料金を cached・uncached・出力に分けて出す
- 先頭から各段（system・道具・会話）の hash を前回と比べ、miss の原因（どこが変わったか）を `/context` に出す
- DeepSeek の peak 時間帯（料金が2倍）を状態の行に出す（時間帯は二次情報なので、公式の頁で確かめてから入れる）

## 機能ごとの影響を書く
この設計に機能を足すときは、それぞれに次の3つを書く。キャッシュを壊す変更を早く見つけるため。
- モデルが見るもの: 足す文や道具の定義
- トークンへの影響: 増える量と減る量
- キャッシュへの影響: 末尾に足すだけか、途中を書き換えるか（書き換えるなら、どこから先が効かなくなるか）

## 言語
言語は役割ごとに分けて設定できる。既定は、人が読むものは日本語、モデルだけが読むものは英語（料金が安いため）。

| 設定 | 既定 | 対象 |
| --- | --- | --- |
| `language.ui` | `ja` | 画面の文（状態の行、確認、エラー、`/help`） |
| `language.reply` | `ja` | モデルの利用者への答え |
| `language.thinking` | `en` | モデルの推論（thinking）。system prompt で指示する |
| `language.modelFacing` | `en` | system prompt、道具の説明、隠した跡の1行、要約の指示と要約そのもの |

`reply` と `thinking` を同じにしたいとき（推論を読みたいときなど）は、`thinking` を `ja` にする。料金は上がるので、`/context` に差の目安を出す。

## 文字のそろえ方（日本語1文字あたりの料金を下げる）
| 設定 | 既定 | 動き |
| --- | --- | --- |
| `text.halfWidthAlnum` | true | ハーネスが作る文（跡、要約、エラー、確認）の数字と英字を半角にする。モデルにも「数字と英字は半角で」と指示する。全角の数字は最大2.5倍、英字は4〜8倍のトークンになるため |
| `text.noFullWidthSpace` | true | ハーネスが作る文に全角の空白を使わない（Gemma 系で1字3トークン） |
| `text.rawUnicodeJson` | true | JSON で日本語を `\uXXXX` に逃がさず、そのまま書く（逃がすと約4倍） |

利用者のファイルの中身と、道具が返す結果の本文は変えない。そろえるのはハーネス自身が作る文と、モデルへの指示だけ。

## 料金の単位
料金は「1つの課題を完全に終えるまでの総額」で比べる。課題は与えられた作業1つで、利用者とのやりとりが何回あってもよく、失敗とやり直し、要約や subagent の呼び出しも含める。実際の使用では、セッションの始めか `/clear` から、次の `/clear` かセッションの終わりまでを1つの課題とみなす（仮。区切り方は使いながら見直す）。

`/model` の一覧の主な数字は、そのモデルの実績の「課題1つあたりの料金（中央値）と往復の数」にする。実績は終えたセッションの usage から `~/.ja-harness/stats.json` にためる。実績がまだないモデルは「実績なし」と出し、単価だけを見せる。

## モデルごとの日本語の料金（参考）
`/model` の一覧に、参考として、モデルごとの「日本語1文字あたりの料金」を出す。値は、価格表の単価 × そのモデルの日本語1文字あたりのトークン数（`prices` の `jaTokensPerChar`。既定は目安の値で、DeepSeek の 0.7 は実測のかな・漢字の値と日本語÷英語の比から見積もったもの。セッションの usage と文字数から更新する）。日本語に強いトークナイザーほど同じ文章が安くなる（日本語÷英語のトークン数の実測: Gemma 3 は1.21倍、DeepSeek-V3 は1.42倍、o200k は1.66倍、旧 Claude は2.13倍。wataaass/nihongo-kit の調査メモ）。

## 設定
上の値はすべて設定ファイルで変えられる。作業フォルダの `.ja-harness/config.json` が、ホームの `~/.ja-harness/config.json` より優先される。

```json
{
  "context": {
    "masking": { "mode": "price", "keepRecent": 10, "batch": 10, "minTurnsAhead": 3, "summarizeBatch": true },
    "summary": { "maxTokens": 64000, "maxRatio": 0.5, "keepRecentTokens": 20000 },
    "maxTurns": 30,
    "toolResultMaxTokens": 2000,
    "fileReadMaxTokens": 8000,
    "thinkingEffort": { "plan": "high", "default": "low" },
    "repoMapMaxTokens": 1000,
    "repeatReminders": [3, 5, 8],
    "pruneBeforeSummary": { "maxTokens": 4000, "headTokens": 2000, "tailTokens": 500 },
    "overflowRetries": 1,
    "cleanShellOutput": true
  },
  "language": { "ui": "ja", "reply": "ja", "thinking": "en", "modelFacing": "en" },
  "text": { "halfWidthAlnum": true, "noFullWidthSpace": true, "rawUnicodeJson": true },
  "models": { "main": "deepseek-v4.1-flash", "light": "deepseek-v4.1-flash" },
  "prices": {
    "deepseek-v4.1-flash": { "input": 0.15, "cachedInput": 0.003, "cacheWrite": 0.15, "output": 0.6, "jaTokensPerChar": 0.7 }
  }
}
```

`masking.mode` を `"off"` にし、`summary.maxRatio` だけで動かせば、「上限の70%で初めて手を入れる」形（Claude Code などに近い）にもできる。測定で両方を比べられるようにするため。

## 測定（最小）
工夫が料金を下げるかを確かめるため、`ja-harness bench` で次を行う。
- 課題: 数件（まず5件ほど）。それぞれに小さなリポジトリと、終わったかを判定する検査のテストを付ける
- 条件: 工夫あり（既定の設定）と、工夫なし（`masking.mode: "off"`、要約はモデルの上限の近くだけ、道具の結果の上限なし）。モデルと課題は同じにする
- 記録: 課題ごとに、総料金（cached と uncached に分けて）、成功（テストが通ったか）、往復の数、トークン数
- 出力: 条件ごとの表と、課題ごとの差。回数が少ないので、結論ではなく目安として扱う

利用者の確認は自動で通す（bench 用の作業フォルダの中だけで動かす）。nihongo-kit の評価の部品（usage の記録、対の比較）を流用する。課題を増やす、複数回まわして安定性を見る、などは次の版に回す。

## 根拠
- 道具の結果の上限: 上限を1,000〜8,000トークンの4段階で比べた研究で、大事な項目を先頭に並べれば1,000トークンでも必要な項目が先頭に来る割合は変わらず、エージェントは2ページ目をまったく取りに来なかった（Agents Don't Paginate、arXiv 2608.26130）。Claude Code は 10,000トークンで警告し、25,000で切る
- masking を常に動かす: observation masking は rolling window（M=10）で最初から動かし、要約と同じくらい解けて費用は約半分だった。短い trajectory でも効き、トークンの約84%は道具の結果だった（The Complexity Trap、NeurIPS 2025、arXiv 2508.21433）
- 要約は最後の手段: 同じ研究の hybrid（masking を常に動かし、約30Kトークンで LLM-Summary）は、masking だけより費用が7%少なく、解けた割合は2.6pt 高かった。要約の呼び出しは、作り方によってはキャッシュが効かず高い（この設計では、会話の先頭をそのまま送ってキャッシュに乗せる）。パラメータを雑に組み合わせると逆に悪化した
- 長くしすぎない: 18モデルで、入力が長くなるほど性能が不安定になった（Context Rot、Chroma 2025）
- KV-cache: prefix を固定し、context は append-only にすると hit rate が上がる。圧縮は、パスや URL を残して restorable にする（Manus、Context Engineering for AI Agents）。tool result clearing は最も安全で軽い compaction（Anthropic、Effective context engineering for AI agents）
- 古くなった読み取り: Complexity Trap は限界として、window が古さを見ない（ファイルを変更したあとも古い中身を残す）ことを挙げている。すぐ隠すのは、この指摘からの推論で、測定で確かめる
- まとめて隠す頻度（10件）は、masking と KV-cache を両立させるための推論で、論文が直接示した値ではない。測定で見直す

- 要約をキャッシュに乗せる、要約の前の切り詰め、あふれたときの再送、くり返しの促し（3・5・8回）、system prompt を途中で変えない: DSH（deepseek-ai/deepseek-harness）の compaction-basic・tool-result-pruner・repeat-tool-reminder の考え方。切り詰めの値は DSH の8,192字（先頭4,096・末尾1,024）を、日本語を考えてトークンで置いた推論の値で、測定で見直す

## まだ決めていないこと
- 推奨値のうち、論文にない値（まとめて隠す10件、要約の64K・50%・直近20K、ファイルの読み取りの8,000）は、測定（最小）の結果で見直す
- 価格表の DeepSeek の値（off-peak の $0.15 / $0.003 / $0.60）は二次資料の値。公式の頁と、応答の `list_cost` で確かめてから既定にする。peak 時間帯の扱いも同じ
- 次の版の測定には、最小の測定の記録に加えて、同じファイルの再読の率と複数回の安定性を入れる
- 道具の結果を「大事な順」に並べる方法（コマンドごとに決めるか、汎用の規則にするか）
