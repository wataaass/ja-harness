# DeepSeek では「隠す」より「壊さない」が効く

ja-harness の主な対象である DeepSeek V4.1 Flash では、cache hit が miss の約50分の1（off-peak で hit $0.003、miss $0.15、1M トークンあたり）なので、費用を決めるのは「文脈の長さ」より「cache を壊さないこと」と「新しく入るトークンと出力の量」である。この前提に立つと、今の設計のいくつかは費用の面で根拠が弱い。10件まとめて隠す observation masking は、単純な模型で元を取るまでに約97往復かかり、DeepSeek V4 Pro の実測でも圧縮による料金の削減は中央値で約2%（95%区間は0をまたぐ）にとどまった。編集したファイルの古い読み取りを「すぐ隠す」決まりは、編集のたびに履歴を書き換えて cache を壊すうえ、読み取りを要約や印に置き換えると str_replace が合わなくなって再読をくり返したという報告がある。thinking の量やモデルの切り替えも、提供元によっては cache を壊す。一方で、設計にまだない工夫で効果が大きく作る量も少ないものがある。大きな出力の全文をファイルに残してパスを返すこと、編集の結果を変わった行だけにすること、読み取りの道具を並列に呼ばせて1つの応答にまとめること、編集のあとに lint を自動で走らせて結果に添えること、cache の hit 率と miss の原因を状態の行に出すこと、の5つである。masking と要約は、費用ではなく質（Context Rot）と文脈の上限のための仕組みと位置づけ直し、提供元の価格から「書き換えるか」を決める形に直すのがよい。この報告は、`docs/research/research_notes/ハーネスのトークン削減技術/` の調査メモ5本と、nihongo-kit 側の②の調査（Haiku・API でキットありのトークンがなしの約7.7倍、Go の枠の減り方が表示価格の約4倍）を土台にしている。数字の多くは各論文や製品の自己申告で、モデルや課題が違うため、横に並べて直接は比べられない。

## 既存の設計と食い違う5つの発見と、その直し方

いちばん大きいのは価格の構造である。DeepSeek V4.1 Flash は書き込みの割増がなく、off-peak で hit $0.003・miss $0.15・出力 $0.60、peak はすべて2倍になる（[deepakness.com](https://deepakness.com/raw/deepseek-v4-1-flash-price/)、[OpenCode Go](https://opencode.ai/docs/go/)）。Anthropic の Haiku 5.5 や OpenAI の GPT-5.6 は hit が通常入力の0.1倍、書き込みが1.25倍なので、miss と hit の差は10〜12.5倍にとどまる（[Anthropic Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)）。なお OpenRouter の一覧は DeepSeek の読みを0.1倍としており、経由する provider によって値が違う可能性がある（[OpenRouter](https://openrouter.ai/docs/features/prompt-caching)）。OpenCode Go は DeepSeek V4.1 Flash の1リクエストを「入力410・cached 71,300・出力310トークン」と見込んでおり、入力の99%以上が cache から読まれる前提で月の回数を出している（[OpenCode Go](https://opencode.ai/docs/go/)）。つまり hit 率が少し落ちるだけで、使える回数が大きく減る。

**一つ目の食い違いは、masking の費用の根拠である。** 書き換えた次の1回に増える費用を C₁ ≈ (P − S)·m − P·h、その後1往復ごとに浮く費用を ΔC ≈ S·h とすると（P は書き換えた位置から末尾までの長さ、S は減るトークン、m と h は miss と hit の単価）、元が取れる往復の数は N* ≈ C₁ / ΔC になる。設計の既定（2,000トークン×10件をまとめて隠し、P = 60K、S = 20K）を当てはめると、**DeepSeek V4.1 Flash では N* ≈ 97往復、Haiku 5.5 や GPT-5.6 では約22往復**になる。これは調査メモで組んだ自前の模型で、一次資料に閉じた式はない。ただ実測もこの向きを支えている。DeepSeek V4 Pro で5課題×5回×3条件を比べた実験では、入力の約92%が cache hit で、キーワードによる圧縮も V4 Flash による要約も料金の削減は中央値で約2%と誤差の範囲だった（[DEV Community](https://dev.to/projectescape/does-compacting-tool-output-lower-a-coding-agents-api-bill-ena)）。CoACT の再現では、Sliding Window がトークンを40.3%減らして料金は8.6%しか下がらず、AgentDiet はトークンを43.7%減らしたのに料金が10.6%増えた。外れた KV-cache の分の uncached 入力が増えたためである（[CoACT](https://arxiv.org/abs/2607.02911)）。ある本番の compaction では、トークンが約41%少ないのに費用が約2倍になったという二次の報告もある（[Towards AI](https://pub.towardsai.net/lai-139-fewer-tokens-cost-us-more-fa1e273f9b1b)。会員限定の記事の検索要約で、弱い根拠）。

質の面でも、masking は思ったほど安全ではない。設計が根拠にした Complexity Trap は「masking は要約と同じくらい解ける」としたが、AttnCompress の比較では ObsMask は料金こそ最も安かった（平均 $0.0443、全文は $0.1189）ものの、Pass は47.17%で全文の55.17%を大きく下回り、手順は45.9から63.5に増えた。Qwen3-235B では46.5%から31.5%に落ちている（[AttnCompress](https://arxiv.org/abs/2609.08318)）。AttnCompress の window の大きさは確かめられておらず、どちらが正しいとは言い切れない。言えるのは、安いモデルで既定の masking が質を落とさないかを、ja-harness 自身が測るまで信じてはいけないということである。

直し方は、masking を「常に動かす」から「価格と状態を見て動かす」に変えることである。提供元の価格から N* を計算し、残りの会話が N* より短いと見込めるうちは隠さない。DeepSeek では、文脈の長さが質のしきい値（後述の要約のしきい値より手前）に近づいたときと、cache が冷えたとき（Anthropic の5分 TTL を超えた idle のあとなど。冷えていればもともと全部 miss なので、書き換えは常に得になる）に、まとめて隠す。Anthropic や OpenAI では N* が約22往復と短いので、今の既定に近い動きでよい。設定の `masking.enabled` と `batch` はそのまま残し、`masking.mode: "cost-aware"` のような選択肢を足して DeepSeek の既定にするのが、設計の「値はすべて設定で変えられる」という方針とも合う。

**二つ目は、古い読み取りを「すぐ隠す」決まりである。** これは編集のたびに過去の履歴を書き換えるので、「書き換えはまとめて1回で行う」という同じ設計の決まりと矛盾し、編集のたびに cache を外す。さらに DeepSeek V4 Pro の実験では、2,000字を超える道具の出力を要約した最初の版でファイルの読み取りが要約になり、search-and-replace が合わなくなってエージェントが再読をくり返した。古い読み取りを「reread」の印に置き換えた版でも、上限まで再読が続いた。著者はそれ以降、ファイルの読み取りは常にそのまま残している（[DEV Community](https://dev.to/projectescape/does-compacting-tool-output-lower-a-coding-agents-api-bill-ena)）。Claude Code は、前に読んだファイルを編集しても履歴の読み取りを書き換えず、「ファイルが変わった」という通知を末尾に足すだけにしている（[Claude Code: prompt-caching](https://code.claude.com/docs/en/prompt-caching)）。ja-harness もこの形に直すべきである。編集の結果に「変わった行と前後数行」を返し、それで最新の中身が末尾にあることを保証する。古い読み取りは、次のまとめての masking の対象に入れるだけにする。`maskStaleReads` の既定は「すぐ」から「次の batch で」に変える。

**三つ目は、道具の結果の上限2,000トークンである。** 製品の多くはずっと大きい。OpenCode と Goose はシェルの出力を2,000行または約50KB（およそ1万〜1.5万トークン）まで入れ、OpenCode は超えた分の全文をファイルに保存して7日残す（[OpenCode tool-output.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/tool-output.ts)、[Goose shell.rs](https://github.com/block/goose/blob/main/crates/goose/src/agents/platform_extensions/developer/shell.rs)）。Claude Code の道具の応答は既定で25,000トークンまでで（[Anthropic: Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)）、SWE-agent は観測1件100,000文字までである（[SWE-agent agents.py](https://github.com/SWE-agent/SWE-agent/blob/main/sweagent/agent/agents.py)）。近いのは Codex の既定10,000バイト（[Codex model_info.rs](https://github.com/openai/codex/blob/main/codex-rs/models-manager/src/model_info.rs)）で、これは英語でおよそ2,500トークンにあたる。第三者の記事は Codex で `tool_output_token_limit` を8,000〜12,000にすることを勧めている（[danielvaughan.com](https://codex.danielvaughan.com/2026/07/03/tokenpilot-cache-efficient-context-management-codex-cli-prompt-cache-compaction-eviction-cost/)）。Agents Don't Paginate の結果は小さな上限を支えるが、それは「大事な順に並べる」ことが前提である。DeepSeek では、大きな結果を一度入れても次からは hit の単価で読めるので、上限を少し上げる費用は小さい。逆に必要な行を切って再読や再実行を招くほうが高くつく。直し方は、シェルと MCP は2,000トークンを残しつつ、超えた分の全文をファイルに保存してパスを跡に書くこと（restorable にする）、ファイルの読み取りには別の上限（たとえば8,000トークン、行の範囲つき）を設けて `toolResultMaxTokens` を道具ごとに分けること、そして切り詰めは結果を最初に入れるときの1回だけにして、後から切り直さないことである。

**四つ目は、要約のしきい値32Kである。** これは Complexity Trap の hybrid（約30Kで要約）には沿っているが、製品の中ではかなり早い。Codex と Cline は窓の90%、Goose は80%（ただし225,000トークンまで）、Amp Neo は90%、OpenCode は窓の15%（最低16,000）を残すところで発動する（[Codex openai_models.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/openai_models.rs)、[Cline compaction-shared.ts](https://github.com/cline/cline/blob/main/sdk/packages/core/src/extensions/context/compaction-shared.ts)、[Goose lib.rs](https://github.com/block/goose/blob/main/crates/goose-context-management/src/lib.rs)、[OpenCode compaction.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/session/compaction.ts)）。もっと早いのは aider だけで、会話の履歴が入力上限の16分の1（1,024〜8,192トークン）を超えると weak model で要約する。ただし aider はファイルを明示して入れる設計で、比べる対象が違う（[aider models.py](https://github.com/Aider-AI/aider/blob/main/aider/models.py)）。OpenCode のソースの注釈によると、実際のセッションでは1回の往復で増える量が p99 で約22,000トークンあった。32Kのしきい値では、重いセッションで数往復ごとに要約が走りうる。要約を重ねる危険は TRACE が示している。くり返すほど「どこまで終わったか」が弱まり、環境に拒まれる行動と前の探索のくり返しが増え、長い課題ほど落ち方が大きい。AppWorld では16K・8K・4K の予算で、FIFO の切り捨てが要約と同等か少し上だった（[TRACE](https://arxiv.org/abs/2608.06503)）。Amp は「要約を重ねると情報が落ちる」として、いったん compaction を外したこともある（[Amp: Handoff](https://ampcode.com/news/handoff)）。費用の面では、DeepSeek で32Kの文脈を全部 hit で読んでも1回 $0.0001 ほどで、要約の出力（1,500トークンで約 $0.0009）と次の1回の miss を足すと、元を取るまで約15往復かかる（自前の概算）。早く要約する費用上の得はほとんどない。直し方は、DeepSeek の既定を「64K かモデルの上限の50%の小さいほう」に引き上げ、32K は設定の選択肢として残し、測定で比べることである。あわせて、要約のあとに直近の生のやりとりを残す（OpenCode は15,000トークン、Cline は20,000トークン）。これは推論で、論文が直接示した値ではない。

**五つ目は、thinking の量の切り替えとモデルの振り分けが cache を壊すことである。** Anthropic では、thinking の設定や `output_config.effort` を変えると messages の cache が無効になり、thinking block を落とすとその位置から後ろが無効になる（[Anthropic Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。cache を保ったまま途中で effort を変えるには、beta の per-message effort を使う必要がある（[Anthropic: Effort](https://platform.claude.com/docs/en/build-with-claude/effort)）。OpenAI でも `reasoning.effort` と `model` は prefix を変える設定に入っている（[OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching)）。cache はモデルごとなので、Claude Code も `opusplan` の計画と実行の切り替えのたびに cache が新しくなると書いている（[Claude Code: prompt-caching](https://code.claude.com/docs/en/prompt-caching)）。DeepSeek には、もう一つ見落としやすい仕様がある。tools を使う会話では、過去の `reasoning_content` をすべて送り返す必要があり、省くと400エラーになる（[DeepSeek API: Thinking mode](https://api-docs.deepseek.com/guides/thinking_mode)）。過去の推論を消して入力を減らす方法（ICLR の手法。入力 -25.5%、[ICLR](https://arxiv.org/abs/2609.29875)）は、DeepSeek では使えない。推論のトークンは次の往復の入力として積み上がるので、thinking を絞ることは入力の削減にも効く。thinking の on/off や `reasoning_effort` を変えたとき DeepSeek の cache がどうなるかは、公式の記述が見つからなかった。直し方は4つある。DeepSeek では `models.light` を本体と同じモデルにする（今の設定例のとおり）。モードの切り替えでは道具の定義を変えず、「今のモード」を末尾の message に書く。thinking の量はやりとりの区切り（利用者の新しい入力）でだけ変え、Anthropic では per-message effort を使う。`reasoning_content` は常に同じ扱いで送り返す。DeepSeek の thinking の切り替えが cache に与える影響は、最初の動作確認で `prompt_cache_hit_tokens` を見て確かめる。

subagent にも注意が要る。Systima の比較（二次資料）では、Claude Code で作業を subagent に任せると合計が121,000から513,000トークン（4.2倍）に増えた（[Developers Digest](https://www.developersdigest.tech/blog/claude-code-token-overhead-opencode-comparison)）。Claude Code 自身も agent teams は通常の約7倍のトークンを使うと書いている（[Claude Code: costs](https://code.claude.com/docs/en/costs)）。ja-harness の subagent は、親と同じ道具の定義と system prompt を先頭に持たせて提供元の側で prefix を共有させ、1つの仕事あたりの往復の上限を小さくし、使った量を状態の行に分けて出すべきである。

## 圧縮は「入れる時に1回」、書き換えは「まとめて少なく」

調査メモが集めた新しい圧縮の手法は、ほぼすべてが同じ教訓に行き着く。文脈に入れる前に1回だけ縮める方法は append-only を壊さないので料金が実際に下がり、すでに入った部分を書き換える方法はトークンほど料金が下がらない。CoACT は「圧縮した出力でも元と同じ次の行動を引き出すか」で圧縮を選び、SWE-bench Verified の3モデル平均で合計トークンを33.0%減らし、PASS@1 を69.0%から71.0%に上げた。同じ論文で、汎用の token 単位の圧縮である LLMLingua-2 は、PASS@1 を57.0%から50.0%に下げ、手順を111%、合計トークンを172%増やした。必要な情報を消すと、取り戻すための呼び出しが増えるためである（[CoACT](https://arxiv.org/abs/2607.02911)）。CoACT の圧縮器は学習した4Bのモデルで、v0.1 にそのまま入れるのは重い。それでも、学習なしで借りられる考え方がある。「縮めたあと、同じ出力をもう一度読みにいく率」と「手順の数」を記録し、再読の率を上げる規則は外す、という評価の物差しである。

学習なしでいちばん効果がはっきりしているのは、ContextSniper の方式である。長い読み取りやコマンドの出力を、指定の範囲、失敗、assertion の文に絞り、元の出力は保存して「短くした」と印を付け、続きを頼めるようにする。SWE-bench Lite で OpenClaw は合計トークン -51.5%（料金 -36.4%）、Claude Code は -38.9%（料金 -27.3%、推定）だった。ただし解決率はどちらも2ポイント下がっている（[ContextSniper](https://arxiv.org/html/2607.01916v1)）。Cursor も長いシェルと MCP の出力を切らずにファイルに書き、`tail` などで必要な部分を読ませている。MCP の道具を必要なときだけ読む方式と合わせて、MCP を呼んだ実行の合計トークンが46.9%減った（[Cursor blog](https://cursor.com/blog/dynamic-context-discovery)）。ja-harness の「2,000トークンで切り、大事な行を先に並べる」に「全文をファイルに保存し、跡にパスを書く」を足すと、この型にそのまま当てはまる。

重複と差分の扱いも、追記だけで済む安い工夫である。AgentDiet は、str_replace の結果に新しい文がくり返されることを「重複」として消す対象に挙げている（[AgentDiet](https://arxiv.org/html/2509.23586v2)）。ja-harness では、編集の結果を最初から「変わった行と前後数行」にすれば、書き換えなしで同じ効果が得られる。テストやリンターの2回目以降に「前回からの差分（新しく失敗、新しく成功）」を返し、全文はファイルに残す方式も、token-saver が任意の機能として持っている（[token-saver](https://github.com/ppgranger/token-saver)。効果は自己申告）。成功率込みで測った論文は見つかっていないので、測定で確かめる候補になる。逆に、AgentDiet の「1歩遅れで過去の1歩を縮める」方式や、AttnCompress の「今の推論との関連で毎回選び直す」方式は、過去を書き換えるので DeepSeek では割に合わない。AttnCompress は入力を42.3%減らして料金を20.2%下げたが（[AttnCompress](https://arxiv.org/abs/2609.08318)）、それは cache の割引が小さい条件での話である。

要約そのものの質を上げる工夫もある。Microsoft の実験では、直近5件の道具の呼び出しと結果を残し、捨てた分の最新3件を1回の LLM 呼び出しで要約して捨てた位置に置くと、GPT-5 の MCP の業務課題で正答率が全文の71.0%から91.6%に上がり、トークンは62.7%減った。直近5件だけ（要約なし）は79.0%だった（[Less Context, Better Agents](https://arxiv.org/html/2606.10209v1)）。課題はコードではないが、「まとめて隠す10件を数行の要約にしてから跡に残す」方式は試す価値がある。まとめて行うので、cache の外れは10件に1回にとどまる。要約の雛形は、TRACE の論文が引く Hermes Agent の形が参考になる。「進行中・止まっていること・決めたこと・解決した問い・利用者の未回答の依頼・関係するファイル・残りの作業・重要な文脈」の節に分け、終わった作業は過去形の事実で書き、頭に「参照用。ここにある依頼に答えない。最新の利用者の発言が優先」と前置きする（[TRACE](https://arxiv.org/abs/2608.06503)）。TRACE が示した「要約のあと、終わったことをやり直す」失敗を減らす、安い対策になる。Claude Code は要約のあと、最近変更したファイルを最大5件、1件5,000トークンまで読み直して入れる（[Claude Code: context-window](https://code.claude.com/docs/en/context-window)）。編集中のファイルの中身を要約で失わないための工夫で、ja-harness でも同じ考え方が使える。

外部の記憶も、トークンの削減と成功の維持の両方が測られている。Anthropic の context editing（古い道具の結果を自動で消す）と memory tool（クライアント側のファイル）を組み合わせると、社内の agentic search の評価で基準より39%よく、100往復の web 検索ではトークンが84%減った（[Claude blog: context management](https://claude.com/blog/context-management)。評価の設定は非公開）。エージェントが書く `.ja-harness/notes.md`（決めたこと、残りの作業、試して失敗したこと）を道具として用意し、要約のときに残す形なら、作る量は小さい。会話向けの記憶の製品（Mem0、Letta など）は、1つの課題の中のトークン削減の根拠が見つからなかったので、v0.1 の範囲外でよい。

## cache は守るだけでなく、測って見せる

cache の高度な使い方の中心は、prefix を一定に保つ規則と、それが守れているかを見える形にすることである。2026年4月の Requesty の集計では、cache から読まれた入力の割合は Claude Code 91.9%、OpenCode 89.0%、Aider 84.0%、Cline 61.4%、Kilo Code 45.5%と、作り方しだいで倍近く開いた（[Requesty](https://www.requesty.ai/data/coding-agent-cache-hit-rate-apr-2026)。標本の数は非公開）。Claude Code は `/usage` に hit 率、miss の回数、作り直したトークン数を出し、miss の原因を「モデルの変更」「effort の変更」「道具の定義の変更」「過去の message の変更」「TTL 超えの idle」など16種類に分けて推定する。hit 率90%以上を健全とみなし、compaction や古い道具の結果の消去による作り直しは「expected rebuild」として別に数える（[wmedia.es](https://wmedia.es/en/tips/claude-code-cost-what-broke-your-cache)、[Claude Code: costs](https://code.claude.com/docs/en/costs)）。ja-harness では、送る前に各段（道具の定義・system・会話）の hash を記録し、前回と比べるだけで同じ診断ができる。状態の行に hit 率を、`/context` に miss の原因を出すのは、「トークンを抑える」というこのハーネスの売りを利用者に直接見せる手段になる。料金の表示は、提供元ごとに違う欄から cached と uncached を分けて読む必要がある。DeepSeek は `prompt_cache_hit_tokens` と `prompt_cache_miss_tokens`、Anthropic は `cache_read_input_tokens`・`cache_creation_input_tokens`・`input_tokens` の3つの和、OpenAI は `cached_tokens` である（[DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache)、[Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching)）。

DeepSeek の cache には固有の癖がある。保存した「cache prefix unit」に完全一致したときだけ hit し、構築には数秒かかり、hit は best-effort である（[DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache)）。subagent を並べて投げるときは、1本目を先に投げて応答が始まってから残りを投げると、共通の prefix に hit しやすい。Anthropic は「cache は最初の応答が始まってから使えるようになる」と明記している（[Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。Anthropic の API を使う場合は、breakpoint を「道具の定義の末尾」「system の末尾」「最後の会話の block」に置き、読みの lookback が20 block までなので、長い会話では途中にも置く（同上）。Don't Break the Cache の測定では、cache で API の費用が41〜80%減り、動的な道具の結果を cache から外すほうが全部を cache するより安定して得だった（[arXiv 2601.06007](https://arxiv.org/abs/2601.06007)）。

料金そのものを下げる工夫として、DeepSeek の peak 時間帯がある。peak は単価がすべて2倍になり（[OpenCode Go](https://opencode.ai/docs/go/)）、時間帯は月〜金の01:00–04:00 と 06:00–10:00 UTC、日本時間では10時〜13時と15時〜19時とされる（[yottalabs](https://www.yottalabs.ai/post/deepseek-v4-1-flash-pricing-specs-v4-pro-routing-2026)。二次情報で、公式の頁では確かめられていない）。日本の利用者の昼の作業時間に重なるので、状態の行で peak かどうかを出すだけでも、急がない作業を夜に回す判断を助けられる。Haiku 5.5 を Go で使う場合は、100K トークンを超えると入力・読み・書きの単価がすべて5倍の段に上がる（[OpenCode Go](https://opencode.ai/docs/go/)）。Haiku では cache より「文脈を100K未満に保つこと」のほうが効く。nihongo-kit の測定で「Haiku は枠の減り方が表示価格の約4倍」だった件は、この段や cache の miss が効いた可能性がある（未検証）。

## 出力は「形式」と「考えすぎ」で減らし、速さの技術は見送る

出力の単価は入力の4倍で、DeepSeek では cache が保たれる限り、費用の大半は出力と新しく足したトークンになる。編集の形式は、設計の str_replace が現状の最良に近い。aider の leaderboard では DeepSeek 系が diff（search/replace）の形式を97〜99%正しく書けており、DeepSeek-V3.2-Exp（Chat）は225課題を $0.88 で70.2%解いた（[aider LLM leaderboards](https://aider.chat/docs/leaderboards/)）。足すべきは「緩い適用」である。aider は空白の正規化やインデントの相対化を外すと編集のエラーが9倍になった（[aider: Unified diffs](https://aider.chat/docs/unified-diffs.html)）。完全一致に失敗したら空白を緩めて探し、それでもだめなら「old_str が見つからない。似た行: 42行目 …」と近い候補を返すと、再読と出力の作り直しを省ける。SWE-agent の分析では、軌跡の51.7%に失敗した編集があり、1回失敗すると最終的な成功率が90.5%から57.2%に下がった（[SWE-agent](https://arxiv.org/pdf/2405.15793)。抜粋からの数字）。編集の道具の引数は path・old・new に絞り、理由や説明の欄を持たせない。JSON の文字列に入るコードは、改行や引用符のエスケープの分だけ出力が増えるためである。

thinking の量の制御は、出力を減らす最大の手段だが、前節のとおり切り替え方を誤ると cache を壊す。DeepSeek は thinking の on/off と `reasoning_effort`（low/high/max の3段。既定は high）を持つ（[DeepSeek API: Thinking mode](https://api-docs.deepseek.com/guides/thinking_mode)）。aider の測定では、thinking を入れると費用がほぼ2倍になり、正答率の上積みは数ポイントだった（claude-sonnet-4 は56.4%から61.3%、$15.82 から $26.58。[aider LLM leaderboards](https://aider.chat/docs/leaderboards/)）。SWE-bench Verified の4,018軌跡を分析した研究では、考えすぎ（overthinking）の点数が高いほど成績が悪く、点数の低い解を選ぶだけで性能が約30%上がり、計算の費用が43%減った（[The Danger of Overthinking](https://arxiv.org/abs/2502.08235)）。安いモデルほど、計画のとき以外は high より low を既定にするほうが、費用と質の両方に効く見込みが高い。ただし DeepSeek V4.1 Flash の段ごとの推論トークン数と正答率の公式の数字はなく、自前で測る必要がある。

見える本文を短くする指示は、例を1つ添えて具体的に書く。Chain of Draft は few-shot なら GPT-4o の GSM8K で出力を205.1から43.9トークンに減らして精度を91.1%に保ったが、zero-shot では Claude 3.5 Sonnet が90.4%から65.5%に落ち、3Bのモデルでも大きく落ちた（[Chain of Draft](https://arxiv.org/html/2502.18600v2)）。推論そのものを prompt で縮めると、安いモデルでは精度を落としやすい。推論の量は API の effort と thinking の切り替えで、本文の長さは prompt で、と役割を分けるのが安全である。Anthropic も Opus 5 について「effort は見える応答の長さを確実には短くしない。長さは prompt で指示する」と書いている（[Anthropic: Effort](https://platform.claude.com/docs/en/build-with-claude/effort)）。速さの技術は見送ってよい。OpenAI の Predicted Outputs は採用されなかった予測のトークンも課金され、tools とも併用できない（[OpenAI: Predicted Outputs](https://developers.openai.com/api/docs/guides/predicted-outputs)）。Cursor や Morph の fast-apply は、別のモデルがファイル全体を書き直すので、課金されるトークンの合計はむしろ増える（[Cursor blog: Instant apply](https://cursor.com/ja/blog/instant-apply)）。

## 往復は「並列」「まとめる道具」「自動の lint」で減らす

往復を1回減らすと、その往復で送り直す prefix の分と、モデルが出す推論と前置きの分が浮く。DeepSeek では prefix の読みは安いので、主に浮くのは出力の側である。いちばん安く効くのは並列の道具の呼び出しである。Systima の比較では、書く・実行する・テストする・直すの多段の課題を、Claude Code は並列の呼び出しで3リクエスト、OpenCode は9リクエストで終えた（[DEV: Dave Kurian](https://dev.to/davekurian/claude-codes-hidden-token-tax-47x-more-before-you-start-4l4m)。二次資料）。Anthropic は、並列にならない原因で最も多いのは履歴の形の誤りで、結果ごとに user message を分けるとモデルが並列の呼び出しを避けるように「学ぶ」と書いている（[Anthropic: Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)）。ja-harness では、読み取り系（read、grep、glob、ls）は並列に実行し、書き込みとシェルは順に実行する。結果は、OpenAI 互換では連続した `role: "tool"` の message、Anthropic 形式では1つの user message にまとめて返す。複数のシェルの呼び出しは、1回の確認画面にまとめて見せる。DeepSeek が並列の呼び出しに対応しているという資料は第三者のものだけで（[AG2 docs](https://docs.ag2.ai/latest/docs/user-guide/models/deepseek-v3/)）、OpenCode Go 経由で実際に試す必要がある。

道具の設計でも往復は減る。Anthropic は、段階をまとめた道具、一覧ではなく検索を返す道具、出力の詳しさを選べる道具を勧めている（[Anthropic: Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)）。具体的には、`read` が複数のパスと行の範囲を受け取る、`edit` が1つのファイルへの複数の置き換えを受け取る、`grep` が一致した行の前後を返して後の read を省けるようにする、の3つである。往復を減らした量を測った公開データはないが、作る量は小さい。

編集のあとの自動の検証は、往復と質の両方に効く。SWE-agent は、大きなエラーを生む編集を lint ではじく仕組みを外すと、解決率が約3ポイント下がった（[SWE-agent](https://arxiv.org/pdf/2405.15793)。抜粋が崩れており、本文の図では確かめていない）。lint と型チェックの結果を編集の道具の結果に短く添えれば、モデルが「lint を走らせる」呼び出しを出す往復が1回浮き、同じ往復の中で直せる。テスト一式を毎回走らせると時間と出力が増えるので、テストは関係するものだけか、モデルが終わりを宣言したときに回す。複数のファイルを順に直す途中では一時的なエラーが正常なこともあるので、拒否ではなく警告にとどめる設定も要る。Claude Code の LSP のプラグインも、「定義へ移動」1回で grep と候補ファイルの読み取りを置き換えられるとしている（[Claude Code: costs](https://code.claude.com/docs/en/costs)）。

先に計画する方式と早く止める方式は、設計の計画モードとくり返しの検出を伸ばす形で使える。LLMCompiler は依存のある呼び出しを DAG として計画して並列に実行し、ReAct より費用を最大6.7分の1にした（[LLMCompiler](https://arxiv.org/abs/2312.04511)）。ただし QA の課題での数字で、観察してから次を決める部分が多いコードの作業にはそのまま当てはまらない。計画モードで「読むファイルと調べる場所」を先に列挙させ、それを並列の read でまとめて実行する、という使い方が現実的である。早く止める研究では、0.6Bの monitor が途中で失敗を予測して実行トークンを14.6〜20.4%減らし、警報のあとにやり直すと解決率が66.6%から71.8%に上がった。何も持たずに最初からやり直すと66.8%で、ほとんど上がらなかった（[Fail-Fast, Restart-Smart](https://arxiv.org/abs/2608.03222)）。学習した monitor は v0.1 には重い。代わりに、同じファイルへの編集の失敗のくり返しや、往復の数が大きく伸びたことを安い合図にして人に確認し、やり直すときはそれまでに分かったことを要約して渡すのがよい。code mode（道具を呼ぶコードを書かせて1回で実行する方式）は、Anthropic の Programmatic Tool Calling で平均トークンを37%減らしたが（[Anthropic: Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)）、安全な sandbox が要り、ふつうのコード編集では途中の結果（ファイルの中身）をモデルが読む必要があるので効果も小さい。CodeAct では弱いモデルで逆効果の例もあった（[CodeAct](https://arxiv.org/html/2402.01030v4)）。v0.1 では見送る。

測定の仕組み（次の版）には、トークン数のほかに、cached と uncached に分けた料金、手順の数、同じファイルの再読の率、複数回の安定性を入れるべきである。AttnCompress と CoACT の結果では、トークンが減っても手順や再読が増える圧縮があり、それはトークン数だけでは見えない。

## 結論

この調査で見方が変わったのは、「トークンを減らす」と「料金を減らす」が DeepSeek ではほぼ別の問題になる点である。cache が50分の1で読める環境では、文脈を短くする操作の多くは料金にほとんど効かず、cache を1回壊すだけで数十往復分の節約が消える。ja-harness の売りは「トークンを抑える」より「cache を壊さず、新しく入る量と出力を抑える」と言い直したほうが正確で、状態の行の hit 率はその主張を利用者に示す数字になる。masking と要約は捨てるのではなく、Context Rot と文脈の上限に対する保険として、価格を見て動く形にする。

もう一つの含みは、設計の推奨値の多くが、cache の割引が小さい条件の論文から来ていることである。Complexity Trap の hybrid も、AttnCompress や AgentDiet の料金の削減も、DeepSeek の価格では同じ結論にならない。逆に、DeepSeek V4.1 Flash で圧縮の方法ごとの成功率と料金を測った資料は1つもなかった。最初に作る測定の仕組みで、価格を見た masking と今の既定を DeepSeek と Haiku の両方で比べれば、それ自体が公開する価値のある結果になる。
