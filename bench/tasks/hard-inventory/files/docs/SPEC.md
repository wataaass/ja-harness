# 注文・在庫・出荷の仕様

この文書は、注文を受け付けてから出荷するまでの決まりをまとめたもの。
金額、在庫、送料、集計の順番や境界は、すべてここに書いたとおりにする。

## 1. 用語

- 商品: 販売する物。`id`、名前、単価、重さ、税の区分、在庫を持つ。
- 明細: 注文の中の1行。商品 id、数量、単価、重さ、税の区分を持つ。
- 注文: 1人以上の顧客が、1つ以上の明細をまとめたもの。
- 引き当て: 注文を受けた時点で、商品の在庫を確保すること。
- 売上: 取り消していない注文の合計金額。

金額はすべて日本円で扱う。小数が出た場合は、その段階で円未満を
四捨五入する。あとでまとめて丸めるのではなく、仕様に書いた順番で
都度丸める。

## 2. 商品と在庫

### 2.1 商品

商品は次の値を持つ。

| 項目 | 型 | 決まり |
| --- | --- | --- |
| `id` | 文字列 | 空でない。重複しない |
| `name` | 文字列 | 空でない |
| `unitPrice` | 整数 | 1 以上。円 |
| `weightKg` | 数 | 0 以上。kg |
| `taxCategory` | 文字列 | `standard`、`reduced`、`exempt` のどれか |
| `stock` | 整数 | 0 以上 |

在庫は商品ごとに1つだけ持つ。同じ商品の明細が複数あっても、
在庫は合計で1つである。

### 2.2 在庫の引き当て

注文を受けるとき、明細の商品ごとに数量を合計する。

1. 同じ商品 id の明細をすべて足し合わせる。
2. 商品ごとに、合計した数量と今の在庫を比べる。
3. 1つでも在庫より多い商品があれば、注文全体を失敗させる。
4. すべて足りていれば、合計した数量を商品の在庫から引く。

比べるのは「明細1行ごと」ではなく「商品ごとの合計」である。
たとえば在庫が10個の商品に対して、6個の明細と6個の明細が並んだ
注文は、合計12個なので失敗する。

失敗したときは、どの商品の在庫も減らさない。一部だけ引かれた状態を
残してはいけない。

引き当てを戻すときも、商品ごとに数量を合計してから在庫に足す。

### 2.3 在庫の更新とキャッシュ

在庫の問い合わせは多いので、商品ごとの在庫をメモリに覚えてよい。
覚えた値は `inventory:<商品 id>` というキーで持つ。

在庫を書き換えたら、その商品のキャッシュを必ず消す。消さないと、
次の注文が古い在庫を見て、足りていると誤って判断する。

キャッシュは次の場合に消える。

- 在庫を書き換えたとき（引き当て、戻し、手動の更新のすべて）
- 明示的に消したとき
- 有効期限を過ぎたとき

在庫の値が 0 のときも、キャッシュには 0 が入っている。0 を
「値がない」と取り違えない。

## 3. 金額

### 3.1 計算の順番

注文の金額は、明細ごとに次の順番で計算する。この順番を入れ替えては
いけない。

1. 小計 = 単価 × 数量（円未満を四捨五入）
2. 割引 = 小計 × 割引率（円未満を四捨五入）
3. 課税対象 = 小計 − 割引
4. 税 = 課税対象 × 税率（円未満を四捨五入）
5. 明細の合計 = 課税対象 + 税

注文全体の合計は、各明細の小計、割引、税、合計をそれぞれ足したもの。
割引は税抜きの小計に掛ける。税は割引後の金額に掛ける。

割引率は 0 以上 1 以下。注文ごとに1つ持つ。すべての明細に同じ
割引率を掛ける。

### 3.2 税率

税率は明細の税の区分で決まる。

| 区分 | 税率 |
| --- | --- |
| `standard` | 10% |
| `reduced` | 8% |
| `exempt` | 0% |

知らない区分はエラーにする。0% の区分でも、割引の計算は行う。

### 3.3 丸め

円未満は四捨五入する。切り捨てでも切り上げでもない。

- 例: 1,050 円の 8% は 84 円
- 例: 1,050 円の 15% の割引は 157.5 円なので 158 円
- 例: 割引後の 892 円の 8% は 71.36 円なので 71 円

## 4. 送料

送料は、注文の明細の重さをすべて足した合計で決める。

| 合計の重さ | 送料 |
| --- | --- |
| 0kg 以上 5kg 以下 | 500 円 |
| 5kg を超え 10kg 以下 | 800 円 |
| 10kg を超え 20kg 以下 | 1,200 円 |
| 20kg を超える | 1,200 円 + 5kg ごとに 100 円 |

区切りは「以下」で読む。ちょうど 5kg は 500 円の段、ちょうど 10kg は
800 円の段、ちょうど 20kg は 1,200 円の段に入る。

20kg を超えた分は、5kg のまとまりごとに 100 円を足す。端数も
1まとまりとして数える。たとえば 21kg は 1,300 円、25kg は 1,300 円、
25.1kg は 1,400 円である。

重さが負の値や数でない場合はエラーにする。0kg は認める。

小計が 10,000 円以上なら送料を無料にできる。無料にするかどうかは
呼び出し側が決め、注文の合計から送料を引く。

## 5. ページ送り

一覧の画面と API は、同じページ送りの決まりを使う。

- `page` は 1 以上の整数。最初のページは 1。
- `pageSize` は 1 以上の整数。
- `total` は全体の件数。
- `totalPages` は `ceil(total / pageSize)`。端数のある最後のページを
  落とさない。
- `items` はそのページに入る要素。全体の件数が 0 のときは空。
- `hasNext` は、今のページより後ろにページがあるか。
- `hasPrevious` は、今のページより前にページがあるか。

たとえば 23 件を 10 件ずつに分けると、3ページになる。3ページ目には
3件が入り、`hasNext` は false になる。

ページが全体のページ数を超えた場合は、`items` を空にして返す。
エラーにはしない。

## 6. 売上レポート

### 6.1 日付の区切り

日別の売上は、日本時間（JST、UTC+9）の日付で区切る。

- JST の 1日は、UTC の前日 15:00 から当日 14:59:59 まで。
- `2024-01-01T14:59:59Z` は JST の `2024-01-01`。
- `2024-01-01T15:00:00Z` は JST の `2024-01-02`。

UTC の日付で区切ってはいけない。UTC で区切ると、日本では 0 時から
9 時までの注文が前の日に数えられ、日ごとの数字がずれる。

### 6.2 集計

- 日別の売上は、日付ごとに注文数と合計金額を足す。
- 取り消した注文（`status` が `cancelled`）は、指定がなければ数えない。
- 金額は注文の `total`、なければ `grandTotal` を使う。
- 結果は日付の古い順に並べる。
- 月別の売上も同じ区切りでまとめ、月の古い順に並べる。

### 6.3 表示

日別の表は、見出しの行と、日付・注文数・売上の行で作る。
区切りはタブ文字にする。金額に桁区切りは入れない。

## 7. 注文の流れ

1. 顧客と明細を受け取る。
2. 商品を引き、明細を作る。単価、重さ、税の区分は商品から写す。
3. 在庫を引き当てる。失敗したらここで終わる。
4. 金額と送料を計算する。
5. 注文を保存する。
6. 取り消すときは在庫を戻し、状態を `cancelled` にする。

在庫の引き当てに失敗した注文は保存しない。保存してから在庫を
引き当てる順番にしてはいけない。

## 8. エラー

- 商品がない: `商品がありません: <id>`
- 注文がない: `注文がありません: <id>`
- 在庫が足りない: `在庫が足りません: <id>（必要 N、在庫 M）`
- 値が不正: 何が不正かを短い日本語で伝える

エラーの文には、利用者が次に何を直せばよいか分かるように、
商品 id や項目名を入れる。内部のスタックや英語の例外名は出さない。

## 9. 確認のしかた

- `npm test` で、見えているテストを実行する。
- 金額、在庫、送料、ページ送り、日付の境目は、テストで確かめる。
- 仕様とテストが食い違うときは、この文書を先に直す。コードだけを
  仕様に合わせず、文書を直さずに済ませてはいけない。

## 10. データの持ち方

- 商品と注文は、`Map` に id をキーとして入れる。入れた順は保つ。
- 同じ id を二重に入れようとしたらエラーにする。
- 商品を書き換えても id は変えない。
- 注文の明細は、受けた時点の単価・重さ・税の区分を写して持つ。
  あとで商品の値段が変わっても、過去の注文の金額は変わらない。
- 一覧は必要に応じて並べ替えるが、保管している順番は変えない。
- 検索は商品名と id の両方を見る。空白だけの検索語はすべてを返す。

## 11. 画面と API の共通の決まり

- 金額、重さ、日付の表示は、画面ごとにばらばらに作らない。
- 一覧は必ずページ送りを通す。全件を一度に返さない。
- エラーの文は日本語で、利用者が次にできることを短く伝える。
- 内部の例外名やスタックは、そのまま画面に出さない。
